# Phase 4 — 蒸留知識 + 企業分析レポートの読み込み（詳細手順）

添削前に以下を読む。**どれも全読みしない**——蒸留知識・企業レポートは `grep` で節を特定して部分読み（1・2・3）、素材・ログは `ls` →frontmatter で当たりを付けて関係するものだけ最大2件（4・5）、提出済み ES は同じ会社のものだけ（6）。目安は合計 60〜70k字（育った蒸留知識では、全読すると 1+2 だけで 160k字に達することがある）。

## 節選択は「節の用途索引」を正とする（重要）

蒸留が進んだ知識ファイル（`全行業共通.md` や主力業界のファイル）は 80k字規模になり、全読できない。そうしたファイルは冒頭に **`## 節の用途索引（ルーティング表）`** を持ち、各節の `用途` / `ES設問タイプ` /（業界ファイルなら）`部門・業態` を宣言している。この表は `/shukatsu-distill distill` が節を追加・改番するたびに更新される**単一の正**なので、**es-coach 側は節番号をハードコードせず、必ずこの表を読んでから読む節を決める**。

手順：索引表だけを先に部分読み（`grep -n "節の用途索引" <file>` で位置特定 → その表を `Read`）→ 該当行を選ぶ → 選んだ節を `grep -nE "^#{2,4} " <file>` で行範囲特定 → `Read` の offset/limit で本文を部分読み。

索引表がまだ無いファイル（seed 直後や 30k字未満の小さいファイル）は全読でよい。部分読みの手間と取りこぼしリスクに見合わない。

## 1. 全行業共通.md（必ず）

`VAULT_SHUKATSU_CHISHIKI/全行業共通.md`。索引表がある場合は、`用途` に **`共通`** を含む節（全設問で読む土台・採点基準）＋ `ES設問タイプ` が今回の設問タイプ（ガクチカ／自己PR／志望動機／長所短所／失敗・挫折）に一致する節を選ぶ。用途が `面接` / `GD` / `WEBテスト` / `情報戦` / `素材` だけの節は **ES添削では読まない**。設問タイプがどれにも当たらないときは索引の見出しを見て関係節を自分で選ぶ。**迷ったら読む**——取りこぼしで添削が浅くなる方が、数千字の節約より損。

## 2. 志望業界に対応する業界ファイル

`VAULT_SHUKATSU_CHISHIKI` 配下で志望業界名に一致するファイル（`金融.md` / `商社.md` / `コンサル.md` / `IT.md` 等、Phase 0 で `ls` したもの）を1件読む。対応ファイルが無い業界なら全行業共通のみで進め、その旨を一言断る。

- **索引表を持つファイルは索引に従って部分読み**：`用途` に `共通` or `ES` を含む節＋`ES設問タイプ` 一致節を選び、さらに `部門・業態` 列で **志望部門に一致する節だけ**を足す（例：資本市場系の志望なら該当する部門節を足し、無関係な運用系の節は外す。`—` は部門を問わず対象）。索引が小節（`└`）を切り出していればそれを尊重する（面接寄りの節でも、その中の一部だけが ES に効くことがある）。
- **索引表を持たない小さいファイル（30k字未満）は全読でよい**。将来それらが肥大化 or 索引表を持ったら、索引に従う扱いへ切り替える。

## 3. 対象企業の企業分析レポート（企業が特定できる場合）

`VAULT_KIGYOU_REPORTS` 配下、ファイル名は `【<企業名>】企業分析レポート.md`。レポートは 20〜46k字あるので**全文 `Read` せず、必要な 3 種類の節だけを `grep -n` で行番号特定 → `Read` の offset/limit で部分読みする**（トークン節約・必須）：

1. **志望部門に対応する部門節を 1 つだけ**。Phase 1 で確定した志望部門に一致する節を選ぶ（例：Operations → オペレーションズ部門の節、IBD → 投資銀行部門の節）。**関係ない部門節は読まない**。部門が判然としないときのみ、小さい「部門サマリー比較表」で当たりを付ける。`grep -nE "^### [0-9]+\." <file>` で節の行範囲を得てから該当節だけ読む。
2. **「求める人材像」の節**（企業全体の公式人物像）。
3. **企業理念／パーパス／コアバリュー**。⚠️ 専用見出しが無く「会社概要」内に埋もれていることが多いので、見出し grep ではなく**本文キーワード grep**（`grep -n "理念\|パーパス\|コアバリュー\|価値観\|Purpose" <file>`）で位置を特定して該当箇所だけ読む。

見つからない場合は `VAULT_KIGYOU_REPORTS` を `ls` で確認し、別表記（英略称・カタカナ）でも探す。それでも無ければ、その旨を一言断り、`/kigyou-report` を案内する。

## 4. 本人素材

`VAULT_SHUKATSU_SOZAI_SELF` 配下（grill で抽出した本人の経験・強み・価値観）：

- `ls` して frontmatter の `theme` で当たりを付け、今回の設問に関係するものだけ読む（ディレクトリが空なら飛ばす）。
- **長所短所・自己PR系の設問では、`VAULT_SHUKATSU_SOZAI_SELF` の親（＝素材/）配下に長所短所の素材フォルダがあればそれも見る**。絶対パスは直書きせず、レジストリキーの親から辿る。
- **経験インベントリを読む前に `$SKILLS_ROOT/tools/experience_inventory_sync.py` を実行する**（添削ログの `episodes_used` から使用状況を自動再集計。数え漏れ・更新忘れを防ぐ）。その後 `VAULT_SHUKATSU_SOZAI_SELF/経験インベントリ.md` を読み、今回のESが使う経験が既出か・何回使われているかを確認する。既に2回以上使われていれば Phase 5 で「この経験は既に〈X社/Y社〉で使用。使い回し感・面接での深掘り耐性に注意」と警告し、別の引き出し（無ければ `/shukatsu-distill grill` で新エピソード発掘）を促す。
- 目的：添削で「あなたが grill で語った〈経験X〉が活きていない／活きている」と本人の実体験に紐づけて指摘するため。一般論ではなく本人専用の助言にする。

### 4.1 素材カードの数字の鮮度チェック（進行中の経験のみ・必須）

経験インベントリの各エピソード（E1, E2…）は**手動維持のスナップショット**で、`experience_inventory_sync.py` が更新するのは使用回数だけ。**経験の中身（数字・状態）は誰も自動では更新しない**。進行中のプロジェクトの数字をカードからそのまま ES に書くと、古い数字が紛れ込む（例：カードでは「公開前・成果なし」のままだが、実際は公開済みで利用者も増えていた、ということが起きる）。

**対象**：今回の ES（本人の原稿・修正提案とも）に入る、**時間とともに変わる記述**だけ ―― 件数・人数・利用者数/訪問数・売上等の成果指標・「公開前」「進行中」「未完了」などの状態。過去に確定した事実（登壇した・合格した・当時の数字として書く値）は対象外。

**手順**：
1. **基準日を取る**：カードに `as_of`（例 `- **as_of**：2026-09-30`）があればそれ。無ければ、その記述が書かれた時点（見出し・「【YYYY-MM-DD 追加】」等の日付）を基準にする。日付が一つも取れなければ「不明」扱い。今日の日付は `date` で取る。
2. **基準日が今日から14日以内** → そのまま使ってよい。
3. **14日超 or 不明** → 最新値を取りに行く：
   - カードに `live_source`（最新値の置き場所：repo の `HANDOFF.md`、データファイル、集計コマンド等）があればそれを読む。
   - 無ければ、カードの「出所」リンク先ノート、および本人の memory（`Claude memory/` のプロジェクト note に「現況は〜を読む」と書かれていることが多い）から最新値の置き場所を辿る。
   - 辿れた → 最新値で書き、**数字の取り方（何を何で割ったか・下限値か等）も控えておく**（面接で聞かれたとき答えられるように）。
   - 辿れない → 推測で更新しない。古い値のまま書きもしない。Phase 5 の前に「〈E番号〉の〈数字〉は〈基準日〉時点です。今の値を教えてください」と**1問にまとめて**本人に確認する。
4. **レポートでの見せ方**：Phase 5 の「事実確認」に `🔄 [カードから更新した数字]：旧〈値〉（〈基準日〉）→ 新〈値〉 ← 出典：〈source〉` として並べる（本人の経験でも、出典を辿れる数字は検証対象として扱う）。**因果の書き過ぎに注意**：数字が改善していても、その改善がエピソードの行動によるものか確認できなければ、「〜の結果」と結ばず中立に書く。
5. **カードへの書き戻しは提案だけ**：経験の定義は本人が手動で維持する欄なので、es-coach は勝手に書き換えない。「〈E番号〉に `as_of`／`live_source` と最新値を書き足しますか？」と聞き、了承されたときだけ書く。

## 5. 過去添削ログ（同じ志望先・設問タイプ）

`VAULT_SHUKATSU_HIKAKU_LOG` 配下：

- `ls` して frontmatter（`company` / `question` / `weaknesses`）で当たりを付け、一致するものを最大2件読む（無ければ飛ばす）。
- 目的：過去に指摘した弱点が今回も出ていれば「前回〈志望先〉でも〈弱点〉を指摘しています」と**再発弱点として横断指摘**するため。複数設問間で本人の主張がブレていないかも見る。本人が同じ穴に何度も落ちないようにするのがコーチの役目。
- `outcome: 未定` のログは、`選考結果一覧.md` から結果を写す（手順は `save-log.md`「outcome の回填と交絡」）。一覧にも無いものだけ、サインオフ時などに一言リマインドする。

## 6. 提出済み ES（同じ会社）

`VAULT_SHUKATSU_ES` 配下。会社別フォルダ（`<会社名>/`）の場合も、ファイル名が `【会社名】部門・プログラム名.md` の平置きの場合もある。`ls` して**同じ会社**のものを全部拾う（表記揺れ：英略称・カタカナ・旧社名も探す）。同じ会社が無ければ飛ばす。

- 読むのは**今回と違う設問・違う部門・違う時期**のもの。今回の ES が入っているファイルは「今回の原稿」として扱う
- 見るのは次の2点だけ（中身の添削はしない）：
  1. **矛盾**：志望動機の軸・「なぜこの部門」・数字（人数・点数・期間）・役割が、同じ会社に出した別の ES と食い違っていないか。ES は人事→各面接官に回覧され、同じ会社の書類は並べて読まれる前提
  2. **使い回し**：同じ会社の別設問・別部門で同じエピソードを使っていないか。部門違いで同じ志望動機を使っているなら、部門ごとの書き分けが要る
- ファイルが長い・数が多いときは、見出し（設問文）と各設問の冒頭3文だけ読み、数字と固有名詞は `grep` で拾う
- 結果は Phase 5 の「同社 ES との整合」に出す
- このファイルの名前を、添削ログの `es_file` に入れる（選考結果一覧と結ぶため）

## 蒸留知識が seed のみ / 空の場合

「蒸留データがまだ少ないため、一般的な就活知識ベースで添削します。素材が蓄積されるほど精度が上がります。」と一言断ってから続ける。seed 由来（出典なし）の記述を根拠にするときは「一般的な就活知識として」と明示し、「内定者は〜」とは言わない。

> [!important] 企業理念・求める人物像との突き合わせ（必須）
> 志望動機・自己PR・ガクチカいずれの添削でも、対象企業の **企業理念／パーパス／コアバリュー** と **公式の「求める人物像」** に照らして、ESがその価値観・人物像に「刺さっているか」を必ず評価する。
> - 「この企業は公式に〈求める人物像 X〉を掲げているが、このESでは〈X〉に触れる／応える要素が薄い／合致している」という形で具体的に指摘する。
> - 単なる業務理解だけでなく、**価値観・カルチャーフィット**の観点を添削に織り込む。
> - 企業分析レポートが存在しない企業の場合のみ、この突き合わせを省略し「企業分析レポート未作成のため、理念との突き合わせは省略」と明記する（評価サマリーの企業適合は `—（未照合）`）。
