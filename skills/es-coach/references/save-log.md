# Phase 8 — 添削ログの自動保存

**確認を取らずに保存する**。タイミングは3つ：

1. **v1 のレポートを出した直後**：下の schema でファイルを作る。`final_version: 1`・`final_score` に v1 の判定・`weaknesses` に v1 の改善点を入れ、`signed_off: false`
2. **v2 以降のレポートのたび**：同じファイルの `final_version`・`final_score`・`weaknesses`（追記）と「修正履歴」を更新する
3. **サインオフ（Phase 7）のとき**：`signed_off: true` にし、「最終版」と「コーチ総評」を書く

本人が途中で提出・中断しても、最後に出した判定がそのまま残る（「A 目前で提出」も `final_score: B`・`signed_off: false` として信号になる）。保存したことはレポート末尾に1行で知らせる（「ログ更新：〈ファイル名〉」）。

ファイル名：`YYYY-MM-DD_[設問略称]_[志望先略称].md`（`VAULT_SHUKATSU_HIKAKU_LOG` 配下。日付は v1 の日）
例：`2026-05-08_ガクチカ_GS.md`

**保存前に `$SKILLS_ROOT/tools/count_chars.py` で字数を確認**し、フロントマターの schema を必ず揃える（横断スキャンが将来数十件でも効くように）。`final_score` は **S / A / B / C / D の1文字だけ**（「B+」「A目前」は不可。A に届いていなければ B）。項目名も下のとおり（`current_score` などに言い換えない）：

```markdown
---
date: YYYY-MM-DD
company: [志望先（正式名でよい）]
company_normalized: [横断マッチ用の正規化キー。英語正式名で統一。例：Goldman Sachs / Morgan Stanley。表記揺れ（MS / モルガン…）を吸収する]
question: [設問文]
question_type: [ガクチカ / 自己PR / 志望動機 / 長所短所 / その他]
final_version: [最終バージョン番号]
final_score: [S / A / B / C / D のいずれか1つ。「S相当」等の曖昧表記は使わない]
signed_off: [true / false。Phase 7 のサインオフを出したら true]
es_file: "[[提出済み ES のファイル名（VAULT_SHUKATSU_ES 配下・拡張子なし）]]"  # 選考結果一覧の行と結ぶキー。無ければ空
outcome: 未定   # 選考結果が判明したら 通過 / 落選 / 辞退 に更新（手動回填）
outcome_date:   # outcome が確定した日付
outcome_components: # この選考で ES と一緒に評価されたもの。「ES単独」/「ES + Webテスト」/「ES + 動画」等。ES単独でなければ outcome は ES の成績とは言えない（交絡）
episodes_used: [E1, E2] # このESで使った本人エピソードのID（経験インベントリの E 番号）。sync がここから使用状況を集計する。新エピソードなら先にインベントリへ定義を追加
weaknesses: [初稿〜途中で指摘した主要弱点をキーワードで列挙。次回 Phase 4 の横断スキャン用。例：結論が弱い, 数字がない, 企業理念に触れていない]
---

# ES添削ログ

## 設問
[設問文]

## 修正履歴

### v1（初稿）
[v1のES文]

**添削レポート（v1）要約：**
[v1の総合評価 + 主要改善点]

### v2（あれば）
[v2のES文]

**添削レポート（v2）要約：**
[v2の総合評価 + 改善された点 + 残課題]

...（バージョン数だけ繰り返す）

## 最終版（v[n]）
[最終バージョンのES文]

## コーチ総評
[最終添削レポートの内容]
```

**保存後、使用状況を自動更新する**：ログ frontmatter の `episodes_used` にこのESで使ったエピソードIDを記録し（新しい経験なら先にインベントリの「核となる経験」へ E＋番号で定義を追加）、`$SKILLS_ROOT/tools/experience_inventory_sync.py` を実行する。使用回数・使用先はスクリプトがログから再集計するので、インベントリを手で数えて更新しない（真実の出所は `episodes_used` 一箇所）。

## outcome の回填と交絡（振り返り時の必須ルール）

**結果の置き場は `VAULT_SHUKATSU_SOZAI_SELF/選考結果一覧.md`**（本人が「結果」列に `書類×` `テスト×` `一次×` `二次×` `最終×` `◎` `辞退` `待ち` のどれかを書く表。1社ずつ聞かずに済むようにするため）。Phase 4 で過去ログを読むとき、`outcome: 未定` のログは `es_file` で一覧の行を引き、結果があれば `outcome` に写す（書類より先に進んでいれば「通過」、`書類×` なら「落選」）。一覧にも無いときだけ本人にリマインドする。一覧の行が足りなければ（ES を出していない選考など）本人に足してもらう。

落選を写すときは **`outcome_components`（ES と一緒に何が評価されたか）も必ず確認する**。ES単独の選考でなければ、落選＝ESの問題とは言えない（Webテスト・動画等が原因の可能性）。逆に、テストと同時の選考でも**通過したなら ES は足りていた**ので、通過は交絡なしの信号として扱える。

## 判定の検証（Phase 7 で毎回）

サインオフのとき `$SKILLS_ROOT/tools/score_calibration.py --brief` を実行し、出た1行（「サインオフ（S/A）後の書類通過：n/m」）をサインオフの末尾に添える。表全体は `score_calibration.py` で見られる。

- 書類の段階だけで数える（面接の結果は ES の良し悪しと別物）
- **S/A で ES 単独の落選が続く**なら、判定表が甘い可能性がある。本人に伝え、落ちた ES と通った ES の差を一緒に見る
- 件数が少ないうちは（目安：S/A が5件未満）傾向を語らない。「まだデータが少ない」と添える
- スクリプトが schema 違反を出したら、そのログを直してから集計する
